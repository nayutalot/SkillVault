## 真正的问题点（按“别的电脑才触发”的概率排序）

**1. doctor 的 CRLF 修复会把非 UTF-8 文本文件永久写坏（乱码制造机）** — doctor.ts:265
`buf.toString('utf8').replace(/\r\n/g, '\n')` 是「按 UTF-8 强解码再重编码」。如果 vault 里有 GBK/ANSI 编码的 `.ps1/.bat/.py/.md`（中文 Windows 记事本默认 ANSI）或 UTF-16LE 的 `.ps1`（PowerShell ISE 保存），点一次「一键修复」就永久变成乱码。本机 vault 全是 UTF-8 所以没事；另一台电脑自己导入的技能文件只要有一个是 GBK 就中招。

**2. 旧版 WSL 不认 `WSL_UTF8=1`，wsl.exe 输出 UTF-16 被按 UTF-8 解码** — wslBridge.ts / wslmon/index.ts
`WSL_UTF8` 需要 2022 年之后的 WSL（0.58+）才生效。另一台电脑如果是老 WSL，`wsl -l -v` 输出 UTF-16LE，按 UTF-8 解码后就是乱码——WSL 页发行版名、doctor 的 WSL 项、sync 的 companion 错误文本全会花。`cleanWslOutput` 只能救 ASCII（剔 NUL），救不了中文。

**3. git 没关 `core.quotepath`** — git.ts:7 和 companion skm.ts:25
中文文件名在 git 输出里会变成 `\346\226\207\346\241\243` 八进制转义（同步页冲突文件清单、doctor 输出里看起来就是乱码）。实测本机全局也没配 `quotepath=false`，只是目前 vault 里目录名都是 kebab-case ASCII 才没露头；同步冲突清单一旦出现中文名（比如 agents 里的中文名 .md）两边都会花。

**4. 默认路径硬编码 `C:\Users\sakuya\...`** — settings.ts:9-10 和 registry.ts:14-19
另一台电脑用户名不是 sakuya 的话，首次启动默认 vault/裸仓/agent 目录全部指向不存在的路径。这不是乱码，但是「换机必踩」的安装问题，顺手一起修。

**5. 低风险残留**：vscode.ts:60 的 `where.exe` 按 UTF-8 解码（VS Code 装在中文路径下时解析失败，静默兜底到系统默认打开，不显示乱码但值得补）；native.ts:31 的 `.exe --version` 未走 chcp 通道（版本号通常 ASCII，风险低）；SKILL.md/agent 预览按 UTF-8 读取（winLinks.ts:307、ipc.ts:435），导入 GBK 编码的 md 时描述会花。

## 修复方案（建议一次做完）

1. doctor CRLF 修复改成**纯字节级替换**（Buffer 上把 `\r\n` 换成 `\n`，不解码不重编码），并对 UTF-16/含 NUL 文件跳过——零乱码风险。
2. git.ts 和 skm.ts 的 gitRun 统一加 `-c core.quotepath=false -c i18n.logOutputEncoding=UTF-8` 前缀参数。
3. settings.ts / registry.ts 默认路径改为运行时从 `os.homedir()` 派生（首次运行写盘时固化）。
4. vscode.ts 的 where 探测走已有的 chcp 65001 通道；SKILL.md 读取加 UTF-16/GBK 探测兜底。
