# Skill Vault 方案（v2，已按你的洞察重构）

## 一、核心架构：双端原生副本 + git 同步

你的原则「WSL 自己扫自己，Windows 自己扫自己」直接推翻了我最初“WSL 用 symlink 指回 /mnt/f”的设计——那样每次 skill 加载、status 扫描都在持续走 9P，正是会崩的负载。改为：

```
                ┌──────────────────────────────┐
                │   git origin（唯一真相源）     │   GitHub 私有仓
                └───────△──────────────▽───────┘
                        │ push/pull（仅 sync 时，走网络，不碰 /mnt）
        ┌───────────────┴────────┬─────────────┴──────────────┐
        │ Windows 工作副本        │       WSL 工作副本           │
        │ F:\SkillVault（NTFS）  │   ~/skill-vault（ext4）     │
        │                       │                             │
        │ 原生 junction：        │   原生 symlink：             │
        │ .zcode\skills\x ─J→   │   ~/.zcode/skills/x ──→     │
        │ .codex\skills\x ─J→   │   ~/.codex/skills/x ──→     │
        │ .agents\skills\x ─J→  │   ~/.agents/skills/x ──→    │
        └───────────────────────┴─────────────────────────────┘
```

- **平时**：两端各自原生扫描/读写，零 9P 流量；agent 加载 skill 也全是本机文件系统操作。
- **同步**：`skm sync` = git commit + pull --rebase + push，走网络到 origin，完全不过 /mnt。skill 都是小型文本，秒级。
- **真相源语义**：物理上两份原生副本，逻辑上一份——git 历史保证一致，冲突走 git 原生合并。F:\SkillVault 是主编辑面。
- 离线兜底：WSL 偶尔可 `git pull /mnt/f/SkillVault`（小仓库偶发跨 9P 可接受），仅作 fallback。

## 二、三个待定决策（你要的方案列表，附推荐）

**1. Vault 位置**

| 方案 | 优点 | 缺点 |
|---|---|---|
| **F:\SkillVault（推荐）** | 数据与代码分离；F 盘是数据盘，重装系统不丢 | 无实质缺点，跨盘 junction 合法 |

**2. CLI 实现语言**

| 方案 | 关键差异 |
|---|---|
| **Python 3.9+ 纯 stdlib（推荐）** | 唯一已确认双端零成本可用：Windows 已确认 3.9.13，任何 WSL 发行版必带 python3；零第三方依赖。junction 需 subprocess 调 `mklink /J`（免管理员，你机器已有成功先例） |
| Node.js ESM | 对 junction 有原生 API（`fs.symlinkSync(…,'junction')`）最干净，但你机器 Node 可用性未确认，WSL 侧需另装 |
| Go 单二进制 | 分发零依赖最干净，但迭代最重，适合日后成熟再重写 |
| PowerShell + Bash 双脚本 | 逻辑写两遍测两遍，长期成本最高，不推荐 |

**3. git 远端**：推荐 GitHub 私有仓（你有 gh CLI）；备选 F: 盘裸仓作 origin（纯本地但备份弱）。

## 三、Vault 仓库结构

```
F:\SkillVault\
├── skills/                  # 所有 skill 真身，一 skill 一目录
├── bin/
│   ├── skm.py               # CLI 本体（Python stdlib only）
│   ├── skm.cmd              # Windows 入口
│   └── skm                  # WSL/Linux 入口
├── registry.json            # agent 注册表（随 vault 同步，每侧只处理本平台条目）
├── .gitattributes           # 强制 LF
└── README.md                # 架构 + 排障

工具放进 vault 仓库本身——任何一侧 clone 即同时获得数据和工具，无独立分发问题。

registry 结构：每个 agent 一条 `{name, platform, skills_dir, include?}`；`include` 可选，实现某 agent 只要部分 skill（v1 默认全量）。

## 四、CLI 命令集

| 命令 | 作用 |
|---|---|
| `skm init` | 初始化 vault：git init、.gitattributes、registry 骨架、绑 origin |
| `skm import <路径>` | 收编散落 skill：拷入 vault → 校验（文件数+大小）→ 原地替换为链接；支持 `--dry-run` |
| `skm link` | 按 registry 链到本平台所有 agent 目录；幂等（正确跳过、错链断链修复） |
| `skm unlink` | 移除链接，vault 保留 |
| `skm status` | skill × agent 矩阵：✓已链 / ✗缺失 / ~错链 / !同名真实目录；只扫本机 |
| `skm doctor` | 断链、CRLF 污染、WSL 脚本缺执行位、agent 目录重复真身 |
| `skm sync` | git add -A → commit → pull --rebase → push |

链接方式：Windows 一律 junction；WSL 用相对路径 symlink（home 内可移植）。

## 六、跨端陷阱与对策

1. **CRLF/LF**：`.gitattributes` 强制 LF + 两端 `core.autocrlf=false`，杜绝永久 diff 抖动
2. **执行位**：Windows 提交的脚本在 WSL 丢 +x → doctor 在 linux 侧自动 chmod +x
3. **vault 搬家**：junction 是绝对路径，`skm link` 幂等重建即可
4. **F 盘缺席**：Windows agent 目录现断链，agent 一般跳过，doctor 报告
5. **命名规范**：强制小写-kebab-case（ext4 大小写敏感/NTFS 不敏感），doctor 检查

### 框架到底解决什么问题

界面本质是 HTML/CSS/JS。不用框架（vanilla）时，数据一变你得手动更新画面：

```js
// vanilla：每次状态变化，亲手找到对应 DOM 改它

用框架则是**声明式**：你只描述“数据长这样时，画面就该长这样”，数据变了画面自动刷新：

```jsx
// React：状态矩阵里一格的渲染逻辑，写一次管所有格子
<td className={cell.status}>{cell.label}</td>
```

咱们 Dashboard 是“skill × agent 的状态矩阵 + 实时刷新”，正是声明式的甜点场景——vanilla 手写会很啰嗦，所以推荐用框架。
